# ADR 0012 — An additive co-write is not a shared-path conflict

- Status: Accepted
- Date: 2026-09-16

## Context

Two applications can own the same managed path. EP-66 and its successors gave
`seihou update` an *ownership closure* requirement to keep that safe: for every
managed path, if any selected application owns it, every application that owns
it must also be selected. It is enforced twice — before anything is fetched by
`ensureOwnershipClosure` in `seihou-cli/src/Seihou/CLI/Update/Selection.hs`, and
again as defence in depth by `validateOwner` in
`seihou-core/src/Seihou/Engine/Reconcile.hs`.

The reasoning behind it is sound and still applies. Regenerating a file
normally means rewriting all of it. If Seihou did that on behalf of one owner
while another owner was not part of the update, the absent owner's content
would be discarded, and nothing on disk would record that it had ever been
there.

That reasoning is about a file someone rewrites wholesale. It is wrong for
`.gitignore`, and `.gitignore` is where it kept firing. Every owner reaches
that file through an *additive patch*: each appends only the lines it needs
(`append-line-if-absent`) or its own marker-delimited block
(`append-section`). Since nearly every module in the ecosystem appends
something to `.gitignore`, a rail meant for real collisions was refusing
almost every targeted update:

```text
Update failed [shared_path_requires_applications]: Path .gitignore is also
owned by application(s) master-plan.
```

The safety argument for the exemption rests on where the generated bytes come
from during an update. For a path with a prior record, `materializeOne` starts
from the *trusted baseline* — the exact bytes the previous successful
application generated, stored under `.seihou/baselines/` — and replays this
run's operations on top of it. That baseline already contains every owner's
content. Replaying only the selected owner's `append-line-if-absent` on top of
it therefore leaves the unselected owner's lines exactly where they were. A
`WriteFileOp` discards the baseline entirely, which is precisely why whole-file
paths must keep the closure requirement.

## Decision

**A path every owner writes through an additive, non-overlapping patch is not a
shared-path conflict, and a targeted update of a subset of its owners is
allowed.**

The additive set is exactly `AppendLineIfAbsent` and `AppendSection`, as
defined by `isAdditivePatchOp` in `seihou-core/src/Seihou/Core/Types.hs`.
`AppendLineIfAbsent` filters out lines already present, so it is idempotent and
commutative. `AppendSection` writes a region delimited by the contributing
module's own comment markers, which no other module's region overlaps.

`AppendFile` and `PrependFile` are **not** additive in this sense, even though
their names suggest they are. They place bytes relative to whatever is already
in the file, so replaying one owner without the others can reorder the result.
The four whole-file strategies — `Copy`, `Template`, `DhallText`, `Structured`
— are likewise excluded.

**The answer is recorded in the manifest, as a single boolean.**
`FileRecord.additiveOnly` is true when *every* contribution to the path is
additive. Both gates ask only that conjunctive question, so one boolean answers
it. This follows
[ADR 0004](0004-the-manifest-is-the-only-record-of-applied-state.md): a fact
about applied state belongs in the manifest. The alternative — re-resolving
every unselected owner's module at update time to recompute the answer — would
mean fetching and evaluating artifacts for applications the user did not ask to
update, in order to decide whether it is safe not to update them.

**An absent field means `False`, and `False` keeps the closure enforced.**
The exemption fails closed. A manifest written before the field existed carries
no answer, so every shared path in it stays under the closure until one
whole-project `seihou update` records the answers.

**The manifest schema version does not move for this field.** It stays at 6.
The key is emitted only when true, so a manifest with no additive-only paths is
byte-identical to one written before the field existed, and a Seihou that
predates the field ignores the key and keeps enforcing the closure everywhere.
No misreading is possible in either direction. This is a deliberate departure
from the 3→4 and 4→5 precedent, which bumped for additive fields an older
reader would have *misinterpreted*; the test here is misinterpretation, not
novelty. See
[ADR 0005](0005-legacy-manifests-convert-through-an-explicit-command.md) for
the general rule this is an exception to, and the reason it is not a
counterexample: the conservative reading is the correct one, so no conversion
command is needed.

**The exemption is checked in two layers, and both must agree.** The CLI
preflight consults the manifest, because selection happens before any candidate
artifact is fetched and the manifest is the only evidence available.
Reconciliation additionally requires every operation *this run* contributes to
the path to be additive. The second layer is what catches a module whose new
version replaced its patch step with a template step: the manifest still says
additive, the candidate is not, and the update refuses before writing anything
rather than trusting the previous release's record.

**Both manifest write paths may only weaken the flag, never strengthen it.**
There are two producers, not one:

- `prepareCandidateManifest`
  (`seihou-core/src/Seihou/Engine/UpdateTransaction.hs`), for `seihou update`.
- `attachApplication` (`seihou-core/src/Seihou/Core/Application.hs`), for
  `seihou run`.

Each runs after executing a *subset* of a path's owners, so its answer covers
only its own contributions. When a prior owner survives outside that subset,
the prior record is the only evidence about how that owner writes the path.
Both therefore compute `candidateAnswer && priorAnswer` whenever a prior owner
is retained, and both preserve the retained owners in `applicationIds` rather
than replacing them with the current run's view. Getting either wrong is
fail-open: it would flip a `False` to `True` for a path a co-owner rewrites
wholesale, opening both gates for a later update that is not safe.

**Broadening a named selection stays opt-in.** Narrowing what counts as a
conflict is the fix for the false refusals. It is not a licence to update
applications the user did not name. When the closure requirement genuinely
still applies, `seihou update <target> --include-shared-owners` expands the
selection to exactly the applications required and reports each one it added.
Without the flag, a named selection means that selection.

## Consequences

`seihou update <one-module>` works in the ordinary case. The rail still exists,
and now fires on the paths it was designed for.

The manifest grew a field that says something no other field could express:
*how* a path is written, not just by whom. `FileRecord` already carried a
single `strategy` and a single `moduleName` for the whole path, neither of
which can represent "two owners, both appending".

A `False` is ambiguous between "an owner writes the whole file" and "this
manifest predates the field". That is the price of a boolean instead of a
per-`ApplicationId` map, and it is paid once, in the error message, which names
both possibilities and tells the user that a no-target update will record the
answer. A per-owner map would have had to be threaded through `FileRecord`,
`DesiredFile`, `DesiredFileOwner`, and both write paths to buy a better
sentence.

Adding a fifth `PatchOp` obliges the author to classify it. `isAdditivePatchOp`
is total with no catch-all, so a new constructor fails the build rather than
silently defaulting either way — and the safe default is not obviously `False`
to someone adding, say, an `insert-after-marker` operation.

A future per-owner refinement is not blocked. Tightening a `False` to "this
owner writes the whole file, that one appends" would relax the gate further for
some paths and is a compatible change; loosening from a map back to a boolean
would not be.
