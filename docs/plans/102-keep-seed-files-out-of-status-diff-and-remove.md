## Purpose / Big Picture

A *seed file* is a file a module creates once and then hands to the project; Seihou never
overwrites, content-tracks, merges into, reports, or deletes it. The manifest
(`.seihou/manifest.json`) records each one as a *seed receipt* in its top-level `seeds` map
(schema 8), separate from the `files` map of managed, hash-tracked files.

This plan makes the three reporting and removal commands honor that. After it:

- `seihou status` lists only managed files under `Tracked files:` (seed files never appear
  as `modified by user`) and prints one extra line, for example
  `Seed files: 7 (created once; owned by the project, not tracked)`, when the project has
  seeds. It prints nothing about seeds when there are none.
- `seihou diff` compares only managed files, and its summary mentions how many seed files it
  did not compare, so a user is not surprised that an edited `CHANGELOG.md` is absent.
- `seihou remove <module>` never deletes a seed file, even if the module's removal steps name
  it; it prints `Keep <path> (seed file; owned by the project)` in the plan, drops the
  module's ownership of each receipt (deleting receipts no other module owns), and reports how
  many seed files it left in place.

The observable win: in a project generated by a module whose `CHANGELOG.md` and `.cabal`
files are seeds, editing those files leaves `seihou status` reporting only real drift.

## Decision Log

- Decision: Status shows seeds as a single count line, not a list.
  Rationale: ADR 0013 makes status a bounded summary; the point of seeds is to remove noise.
  The full list is in the manifest (`jq '.seeds | keys' .seihou/manifest.json`).
  Date: 2026-09-19

- Decision: Status does not check seed files against disk at all (not even for deletion).
  Rationale: A deleted seed is a legitimate project decision, not drift. Checking would
  reintroduce the noise seeds exist to remove.
  Date: 2026-09-19

- Decision: `seihou remove` never deletes a seed file, including when a recorded removal step
  names it; the step is shown as `Keep` and skipped.
  Rationale: EP-1 rejects such steps in new modules, but manifests store the removal spec
  recorded at apply time, and a module could have been applied before it marked the path as a
  seed. "Never deletes" must hold regardless.
  Date: 2026-09-19

## Context and Orientation

The repository is a Haskell (GHC 9.12) Cabal workspace: `seihou-core/` (domain library),
`seihou-cli/src/` (library `seihou-cli-internal`), `seihou-cli/src-exe/` (the `seihou`
executable). Read `CLAUDE.md` first: strict record fields, `generic-lens` labels for every
field access and update (`m ^. #seeds`, `m & #seeds %~ Map.delete p`), no record dot or update
syntax, `import Data.Generics.Labels ()` per module.

What EP-2 provides (verify before starting): `Seihou.Core.Types.SeedRecord` with fields
`moduleName :: ModuleName`, `applicationIds :: Set ApplicationId`, `outcome :: SeedOutcome`
(`SeedCreated | SeedFoundExisting | SeedReleasedFromManaged`), `settledAt :: UTCTime`;
`Manifest.seeds :: Map FilePath SeedRecord`; and in `seihou-core/src/Seihou/Core/Seed.hs`:
`dropSeedOwner :: Set ApplicationId -> FilePath -> Manifest -> Manifest` and
`seedsOwnedByModule :: ModuleName -> Manifest -> Map FilePath SeedRecord`. A path is never in
both `files` and `seeds` (the decoder enforces it).

**Status.** `seihou status` is `handleStatus` in `seihou-cli/src-exe/Seihou/CLI/Status.hs`. It
calls `Seihou.Core.Status.computeTrackedFileStatuses` (`seihou-core/src/Seihou/Core/Status.hs`),
which iterates only `manifest ^. #files` and compares each file's disk hash with the recorded
hash, producing `TrackedFile { path, moduleName, status }` with `TfsUnchanged`,
`TfsModified`, or `TfsDeleted`. Because seeds are not in `files`, they are already excluded
from this list; this plan adds the summary line and a test that pins the exclusion. Rendering
is the pure function `formatStatusWith` in `seihou-cli/src/Seihou/CLI/StatusRender.hs`
(around line 82), which concatenates sections: recipe, blueprint, blueprint migrations,
applied modules, `trackedSection` (around line 223, prints `Tracked files: N` and one row per
file), `varsSection` (`Variables: N resolved`), update summary, and recommended actions.
[ADR 0013](../adr/0013-status-is-a-bounded-summary-the-manifest-is-the-record.md) governs this
output: status is a bounded view; the manifest is the record.
`seihou-cli/test/Seihou/CLI/StatusSpec.hs` tests `formatStatus` with in-memory manifests.

**Diff.** `seihou diff` is `seihou-cli/src/Seihou/CLI/Diff.hs`: `handleDiff` reads the
manifest, calls `computeTrackedFileStatuses`, and prints `formatDiffOutput color tracked`,
which lists modified and deleted files and a summary line (or
`No changes since last generation.`). Tests: `seihou-cli/test/Seihou/CLI/DiffSpec.hs`.

**Remove.** `seihou remove MODULE` is `handleRemove` in `seihou-cli/src-exe/Seihou/CLI/Remove.hs`.
It requires the applied module's recorded `removal` spec, builds removal operations with
`Seihou.Engine.Remove.buildRemovalOps` (`seihou-core/src/Seihou/Engine/Remove.hs`, around line
139; `buildStepOp` around 161 turns each declared step into a `RemovalOp` — `DeleteFileOp path status`
with status `RFSafe`, `RFConflict`, or `RFGone` from `classifyFileStatus` around line 200,
`StripSectionOp`, `RewriteOp`, `RemovalCommandOp`), displays them with `displayOp`, resolves
conflicts, runs `executeRemovalOps` (around line 219), and finally
`removeFromManifest` (around line 351) drops the module entry and every `files` record whose
`moduleName` is the module. Tests: `seihou-core/test/Seihou/Engine/RemoveSpec.hs`.

Note that `seihou remove` works by *module name*, not by application. A receipt's
`moduleName` is the module that supplied the content, and `applicationIds` lists every
application that seeds the path. To drop a module's ownership, find the manifest's
applications (`Manifest.applications`, each an `AppliedComposition` with an `applicationId`)
that contain the module and call `dropSeedOwner` with those IDs; then delete any receipt whose
`moduleName` is the removed module and that has no remaining application. Inspect
`AppliedComposition` in `seihou-core/src/Seihou/Core/Types.hs` (around line 694) to see how
an application lists its module instances.

Relevant ADRs: [ADR 0013](../adr/0013-status-is-a-bounded-summary-the-manifest-is-the-record.md)
(bounded status), [ADR 0004](../adr/0004-the-manifest-is-the-only-record-of-applied-state.md)
(the receipts are the record), [ADR 0015](../adr/0015-diagnostics-name-things-as-users-do-and-never-fall-back-to-show.md)
(user-facing wording names paths and modules as users write them), and ADR 0017
(`docs/adr/0017-a-seed-file-is-created-once-and-belongs-to-the-project.md`, from EP-1), which
this plan amends.

## Validation and Acceptance

With a manifest containing seeds: `seihou status` lists no seed path and prints the count
line; `seihou diff` reports only managed changes and the "seed files not compared" count;
`seihou remove <module> --dry-run` shows `Keep` for a seed named by a removal step, and a real
removal leaves every seed file on disk byte-identical while the module's receipts disappear
from `.seihou/manifest.json`. All tests pass, including the new ones, which fail before this
plan.


## Idempotence and Recovery

Status and diff are read-only. `seihou remove` already writes the manifest only after
executing its operations; seed handling adds no disk mutation, so a failed removal leaves seed
files exactly as they were. Re-running a removal for a module no longer applied fails with the
existing "not applied" message.
