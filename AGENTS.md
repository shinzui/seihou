# Seihou Agent Instructions

These instructions apply to work in this repository.

## Developer Experience Is an Acceptance Requirement (IMPORTANT)

**A feature is not complete if its intended users cannot use it through a practical, discoverable workflow. Passing tests, sound internals, and completed ExecPlan milestones do not compensate for an unusable developer experience.**

- **Design the user workflow before the implementation.** State the user's starting state, intended outcome, and exact normal command sequence. Consider first use, adoption by existing projects, fresh clones/worktrees, repeated use, and recovery where relevant. Put this concise acceptance scenario in the existing plan or task; do not create extra planning paperwork for a simple change.
- **Minimize the total burden on the developer.** Count required commands, flags, prompts, manual edits, prerequisite knowledge, and time across the entire workflow, including one-time adoption. For a simple intent, aim for one ordinary command. Justify unavoidable additional steps and automate deterministic preparation inside the tool. A long command, script, or wrapper that still requires users to understand internal dependencies is not a usability fix.
- **Make the normal command own the normal workflow.** Resolve known dependencies, reuse recorded inputs, and integrate routine migration/adoption into the appropriate public command. Do not require users to enumerate transitive modules, inspect/edit internal JSON, manipulate the Git index, or discover implementation-specific ordering for routine use. Preserve user changes and safety boundaries; present consequential transitions clearly within the normal preview/confirmation flow.
- **Prove the ordinary path early.** Before expanding implementation or test coverage, exercise a representative real consumer from its actual pre-change state using the commands a developer would naturally run. Include empty caches and older supported state when relevant. Fixture preparation, manual repairs, privileged agent knowledge, and special flags must not silently perform steps the shipped workflow leaves to the user. Count every required preparation step in acceptance.
- **Review the human interface as well as the result.** Default output and help must explain what happened, whether the task succeeded, and the exact next action when blocked. Normal use must not require JSON output or reading source code. Avoid alarming warnings for optional caches or healthy states. Verify that suggested commands are necessary and actually supported before recommending them.
- **Own delivery across boundaries.** When the requested outcome depends on producers, consumers, migrations, packaging, or releases, include that integration in the delivery scope. An engine-only milestone may be complete while the user-facing feature remains incomplete. Splitting work across repositories or plans must not drop the original acceptance obligation or force the user to discover missing adoption work.
- **Verify what the user can actually run.** Record which executable/version and published artifacts passed the workflow. Distinguish a source build, an available release, and the user's installed version. Do not describe a source-only fix as delivered to the user. If a required release or authorized installation step remains, state that gap and keep the corresponding delivery work open.
- **Treat excessive friction as a defect in the requested outcome.** When the workflow is cumbersome or the user reports it unusable, reproduce that experience and simplify it within the existing work. Do not defend completion with test counts, document a workaround as the permanent solution, or require the user to commission another ExecPlan for missing usability. Report the verified user workflow and remaining limitations when handing off.
